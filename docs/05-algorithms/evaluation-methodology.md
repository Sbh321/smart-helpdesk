# Algorithm evaluation methodology

How the baseline algorithms are measured so the report's result analysis is reproducible, and so that replacement strategies can later be compared on the same data ([ADR-0023](../adr/0023-minimal-replaceable-algorithms.md)). Experiment list and report tables: [12-academic/result-analysis-plan.md](../12-academic/result-analysis-plan.md).

## 1. What kind of question each experiment answers

| Algorithm | Kind of task | Ground truth | Measures |
|---|---|---|---|
| Priority (E3) | scoring behaviour | hand-written scenarios | scenario table, level changes under weight changes, ageing curve |
| Assignment (E1) | load balancing | none — policies are compared | standard deviation, maximum and minimum load, Jain's fairness index, capacity overflows |
| Duplicates (E2) | retrieval | labelled ticket pairs | precision, recall, F1 per threshold, Recall@5 (accuracy is not used because non-duplicates dominate [Manning et al.]) |
| SLA (E4) | correctness | hand-computed timelines | expected vs actual due times and states, single notification per event |
| History (E6) | correctness and cost | recorded versions | reconstruction correctness, rebuild agreement, report latency, write overhead |
| Performance (E5) | measurement | — | median and 95th-percentile latency, error rate |

Formulas used in the report:

```text
precision = TP ÷ (TP + FP)      recall = TP ÷ (TP + FN)      F1 = 2 × P × R ÷ (P + R)
Jain's index J = (Σ xᵢ)² ÷ (n × Σ xᵢ²)      (1 = perfectly equal load, 1/n = all load on one agent)
```

## 2. Datasets (versioned, committed)

| Dataset | Content | How it is made |
|---|---|---|
| `experiments/datasets/v1/workload/` | 8 agents (skills, capacities 5–12), 6 categories, 500 tickets with arrival times | `php artisan experiment:generate-workload --seed=42` (exponential inter-arrival times, fixed seed) |
| `experiments/datasets/v1/duplicates.json` | 300 labelled pairs: 100 duplicates (60 generated by dropping or swapping words, 40 hand-written), 200 non-duplicates (50 from the same category) | generator with a fixed seed + a hand-written file |
| `experiments/datasets/v1/priority-scenarios.json` | 12 tickets with the expected level | hand-written |
| `experiments/datasets/v1/sla-scenarios.json` | 10 timelines with expected due times and states | hand-written |

A dataset is never regenerated in place; a change creates `v2`.

## 3. Reproducibility rules

1. One seed per run, passed on the command line and printed in every output file.
2. A frozen clock for all time-based experiments.
3. Every run writes CSV/JSON tables plus `run.json` (strategy name and version, settings, seed, git commit, PHP and PostgreSQL versions).
4. The strategy under test is a parameter: `php artisan experiment:run e2 --strategy=baseline`. A future strategy is evaluated with the same command and datasets.
5. `just reproduce` regenerates every table and plot; a test checks that two runs with the same seed produce identical files.

## 4. Procedures

- **E1 assignment:** replay the 500 tickets in arrival order; each ticket is resolved after a generated handling time so load rises and falls; record every agent's open tickets after each assignment; compare random, round robin (skills respected) and the baseline; report the final and time-averaged measures.
- **E2 duplicates:** compute the Jaccard score for each pair; for thresholds 0.10 to 0.90 in steps of 0.05 compute TP, FP, FN, TN, precision, recall and F1; pick the threshold with the highest F1 on 70 % of the pairs and report the numbers on the other 30 %; embed the 100 duplicates in 5 000 generated tickets and report Recall@5 of the suggestion list; repeat with title-only word sets.
- **E3 priority:** compute scores for the scenarios; for each weight try −0.1 and +0.1 (other weights rescaled so the sum stays 1) on 200 generated tickets and count level changes; plot the score of one ticket as it waits 0–96 hours.
- **E4 SLA:** run the timelines with the frozen clock; tabulate expected versus actual.
- **E5 performance and E6 history:** see [performance-testing.md](../10-quality/performance-testing.md) and [history-and-time-analytics.md](history-and-time-analytics.md) §9.

## 5. Threats to validity (to state in the report)

Generated data is easier than real tickets; one person labelled the hand-written pairs; weights and thresholds were chosen by hand; all measurements come from one machine; the baselines are intentionally simple, so results show a working, measurable starting point rather than the best achievable quality.
