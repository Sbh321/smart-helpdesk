# Tenancy at the database level

Application-level design: [03-architecture/tenancy.md](../03-architecture/tenancy.md). Decision: [ADR-0006](../adr/0006-multi-tenancy-model.md). This page is the SQL contract.

## `tenant_id` conventions

- Every application-plane table has `tenant_id uuid NOT NULL REFERENCES tenants(id)`; `audit_logs.tenant_id` and `roles.tenant_id` are nullable (platform-level rows / global roles).
- Control-plane tables (`tenants`, `domains`, `platform_users`, `platform_settings`, framework tables) have none.
- Secondary tables (comments, events, timers, deliveries, pivots) carry `tenant_id` too, even though it is derivable, so RLS is uniform and indexes can lead with it.
- `tenant_id` is filled by `BelongsToTenant` on create and is immutable (a `BEFORE UPDATE` trigger raises on change — the one trigger in the schema).

## Cross-tenant foreign keys

A plain FK `tickets.contact_id → contacts.id` would accept a contact from another tenant. For the hot relations we use **composite foreign keys** so the database itself refuses cross-tenant links:

```sql
ALTER TABLE contacts ADD CONSTRAINT contacts_tenant_id_key UNIQUE (tenant_id, id);
ALTER TABLE tickets ADD CONSTRAINT tickets_contact_fk
  FOREIGN KEY (tenant_id, contact_id) REFERENCES contacts (tenant_id, id);
```

| Child | Composite FKs |
|---|---|
| tickets | contact, organization, category, team, assigned_agent (agent_profiles), duplicate_of (tickets) |
| ticket_comments, mediables, ticket_events, ticket_assignments, ticket_sla_timers, ticket_duplicate_suggestions | ticket (and candidate ticket) |
| agent_skills, team_members, category_skill | both sides |
| ticket_sla_timers | policy |
| webhook_deliveries | subscription |
| contacts | organization |

Everything else (e.g. `priority_override_by → users`) relies on application validation, RLS and the isolation tests. The `(tenant_id, id)` unique constraints cost one extra index per referenced table and are worth it: they turn a class of bugs into constraint violations.

## Row-level security

Policy template applied to every tenant table:

```sql
ALTER TABLE {table} ENABLE ROW LEVEL SECURITY;
ALTER TABLE {table} FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON {table}
  USING      (tenant_id = current_setting('app.current_tenant', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::uuid);
```

Nullable variants:

```sql
-- roles: global rows visible to everyone, tenant rows only to their tenant
CREATE POLICY tenant_isolation ON roles
  USING (tenant_id IS NULL OR tenant_id = current_setting('app.current_tenant', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::uuid);
-- audit_logs: platform rows (NULL) are readable only through the owner connection
CREATE POLICY tenant_isolation ON audit_logs
  USING (tenant_id = current_setting('app.current_tenant', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::uuid);
```

Generated by one migration:

```php
foreach (TenantTables::all() as $table) {          // single source of truth, also used by the reflection test
    DB::statement("ALTER TABLE {$table} ENABLE ROW LEVEL SECURITY");
    DB::statement("ALTER TABLE {$table} FORCE ROW LEVEL SECURITY");
    DB::statement("CREATE POLICY tenant_isolation ON {$table} USING (...) WITH CHECK (...)");
}
```

Semantics: with the setting unset, `current_setting(..., true)` returns NULL and the predicate is NULL → zero rows (fails closed). `TRUNCATE` bypasses RLS and is not granted to the app role.

## Roles and grants

```sql
CREATE ROLE helpdesk_owner LOGIN PASSWORD '…';
CREATE ROLE helpdesk_app   LOGIN PASSWORD '…' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
GRANT CONNECT ON DATABASE helpdesk TO helpdesk_app;
GRANT USAGE ON SCHEMA public TO helpdesk_app;
ALTER DEFAULT PRIVILEGES FOR ROLE helpdesk_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO helpdesk_app;
ALTER DEFAULT PRIVILEGES FOR ROLE helpdesk_owner IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO helpdesk_app;
-- append-only tables
REVOKE UPDATE, DELETE ON audit_logs, ticket_events, sla_events FROM helpdesk_app;
```

The roles are created by the PostgreSQL container's init script (`infra/compose/postgres/init.sql`) in dev and by the Ansible `app` role on servers; CI creates them in the service container before migrations. Migrations run as `helpdesk_owner`; the application connects as `helpdesk_app`.

## Setting lifecycle

| Moment | Statement | Where |
|---|---|---|
| `tenancy()->initialize($tenant)` | `SET app.current_tenant = '<uuid>'` (session-level, no pooler) | `RlsTenancyBootstrapper::bootstrap` |
| `tenancy()->end()` / request terminate / job processed | `RESET app.current_tenant` | `RlsTenancyBootstrapper::revert` |
| Queue worker between jobs | `end()` by the queue bootstrapper; new job re-initialises | stancl `QueueTenancyBootstrapper` |
| Scheduler iterating tenants | `tenancy()->run($tenant, fn)` sets and resets per tenant | commands |
| Platform provisioning | uses `pgsql_owner` connection (owner role, still subject to `FORCE` policies → sets the new tenant's id explicitly before seeding) | `ProvisionTenant` |
| Tests | `RefreshDatabase` runs migrations as owner; tests connect as app role with the tenant set by `actingAsTenant()` helper | Pest |

PostgreSQL reconnects (e.g. after `DB::reconnect()`) lose the setting; the bootstrapper listens to Laravel's connection events and re-applies it.

## Notifications table

Laravel's `notifications` table is polymorphic on `notifiable` and has no tenant column; a user who belongs to two tenants (V1) would see a mixed feed and the table could not be RLS'd. The migration adds `tenant_id uuid NOT NULL`, the `Notification` model uses `BelongsToTenant`, and the database notification channel is wrapped so `tenant_id` is filled from the current tenant.

## Per-tenant counters

```sql
UPDATE tenant_counters SET next_ticket_number = next_ticket_number + 1
WHERE tenant_id = $1 RETURNING next_ticket_number - 1 AS number;
```

Executed inside the ticket-creation transaction; the row lock serialises concurrent creations per tenant, giving gapless numbers (a rolled-back transaction rolls the counter back too). Sequences are not used because they are neither per-tenant nor gapless.

## Testing RLS

| Test | Method |
|---|---|
| Policies exist | query `pg_policies` for every table in `TenantTables::all()`; assert `ENABLE` and `FORCE` via `pg_class.relrowsecurity`, `relforcerowsecurity` |
| App role is safe | `SELECT rolbypassrls, rolsuper FROM pg_roles WHERE rolname = current_user` → both false; `SELECT tableowner FROM pg_tables` ≠ current user |
| Leak test | seed tenants A and B as owner; connect as app role with `app.current_tenant = A`; for every table assert `count(*) WHERE tenant_id = B` is 0; assert `INSERT ... tenant_id = B` raises `42501` |
| Fail-closed | with the setting unset, `SELECT count(*) FROM tickets` = 0 |
| Raw query backstop | a deliberately unscoped `DB::table('tickets')->count()` under tenant A returns only A's rows |
| Reflection | every Eloquent model is classified (primary/secondary/global) and its table is in `TenantTables::all()` or the global list |

## Dedicated-database migration path

1. Set `tenants.placement = 'dedicated'`, create the database and roles (job).
2. Enable `DatabaseTenancyBootstrapper` for dedicated tenants only (custom bootstrapper checks placement) and add `HasDatabase` to `Tenant`.
3. Run `tenants:migrate --tenants=<id>`; copy rows (`pg_dump --table` with `WHERE tenant_id`) into the new database; verify counts; flip placement; delete rows from the shared database.
4. `tenant_id` columns, composite FKs and RLS remain in the dedicated database unchanged (harmless); the setting is still applied.

No MVP work beyond the `placement` column and the bootstrapper seam.
